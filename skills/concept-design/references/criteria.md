# 论证与边界判据

焦点：候选行为是否兑现一个需要，边界是否合理？以下分组是本仓对 Jackson 资料的综合，不是作者固定流程。

## 论证先于边界结论

依声明前提逐步推演 actions/state 是否支持 OP，再说明可观察结果为何满足 purpose。检查隐含条件、跳步及真实场景中的反例；证据不足保留未决，不能以更漂亮的目的描述修复行为缺口。

例如“删除后移入 Trash”只解释存储变化；若目的为恢复误删，OP 须展示恢复，契约也须支持恢复。代码即使完全实现前者，仍未说明如何兑现目的。

## 资格与边界

| 判断 | 定义与决策依据 |
| --- | --- |
| 用户可感 | 使用者能体验价值；API 程序员也是用户 |
| 语义性/行为性 | 表达有意义的动态功能；控件、分类、属性本身不足以成立 |
| 目的性/端到端 | 独立产生可评价价值，行为延伸到兑现需要的结果 |
| 专一 | 一个不可分目的；多目的的 conflation 提示拆分 |
| 完整 | 具备兑现目的的功能；fragmentation 提示合并或补齐 |
| 独立 | 定义无需其他 concept；共享身份用不假定字段的类型参数 |
| 熟悉 | 优先沿用已知概念及惯例；新概念需有既有概念/组合不能提供的价值 |

作者资格教程的八项在此分组，Reusable 放在组合后检验；复用常是良好边界的结果，不是充分条件。同一概念在组合中应保持名称、目的和行为含义（integrity）。

## 场景与调整

实体通常是状态类型；表/类/微服务是实现组织；register 等通常是动作；故事/feature/workflow 是场景切片；跨概念触发是 sync。名称只是线索，只有独立目的和完整行为才支持另立 concept，不能据目录或词性判断。

- split/merge 调整控制力与简单性；unify/specialize 调整通用与贴合。
- tighten/loosen 调整自动化与用户控制，须有欠/过同步的具体场景。

逐候选给结论及依据：保留、拆分、合并、参数化、降级为 type/action/implementation、移至 sync 或待确认。
