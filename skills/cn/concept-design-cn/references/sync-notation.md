# Sync 语义与组合检查

应用目的说明整体需要；概念选择与 sync 共同决定应用行为。先定义端到端场景，再把动作完成关联为后续调用；每段规则说明对场景结果的作用，组合仍保持各概念契约。格式采用 WYSIWID v1 记录模式及标明的本地扩展；它不等同于某个引擎的可执行语法。

## 组合步骤

1. 按 [规格契约](spec-format.md) 核对参与概念、入口签名、结果 case 和实例化；用 [订位例](example-reserving.md) 对照数据依赖拆规则。
2. 每条规则对应一个可解释的设计决策；只匹配所需字段，成功与错误须可区分。为多个 when 保留 flow 及对象关联。
3. 查 where 的零/多组绑定、then 的必填输入及未来输出依赖；按入口覆盖响应、拒绝及部分完成后的失败策略。
4. 推演并发、重放与循环，确认组合保持概念行为；校验/授权在写入前完成，状态查询不能替代写动作原子不变量。

## Flow、图与覆盖

运行时 flow 是外部事件引发的因果实例；Requesting 表达请求，定时/消息可有明确入口。文档 `// flow:` 按职责组织，共享规则身份唯一。需响应的入口覆盖成功、拒绝、故障及关联；后台可无响应，未使用动作列应用排除表。

同步图每 sync 一个规则节点：多 when 连入、多 then 连出，where 另标查询。简化 A→B 图须保留规则名与合取说明，不表示产品依赖。循环须有终止/受控持续运行依据；工程上限截断须可观察。

## 应用场景与设计信号

- 欠同步：应有联动遗漏 → tighten；过同步：自动化夺走用户控制 → loosen/配置。判断依据是应用目的与具体场景。
- Placeholder action 为 access/notify 等可同步能力预留动作，仍须契约；synergy 指组合产生额外价值，扭曲概念原目的则重审。
- 多参与者/长 flow 只是线索；独立目的和自有业务状态才支持重审概念边界，日志/队列不自动成为概念。

## 依赖与产品子集

Intrinsic dependency 指概念定义依赖另一概念，应通过参数化/组合消除。Extrinsic dependency 是应用选择：纳入 A 只有在纳入 B 时才有意义；在总体 PRD 写 `A → B`。

Parnas 原则要求实现支持有意义子集，代码耦合不能证明产品必须依赖。闭包之外还查目的、入口、剩余 sync 与外部资源；分组不自动可交付，有环按依赖组处理。
